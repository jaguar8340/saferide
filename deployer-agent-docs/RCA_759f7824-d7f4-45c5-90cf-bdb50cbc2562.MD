# RCA — `GET /api/students` returns 500 on production (saferide.ch)

## Verdict
NOT a deploy failure, NOT a package/version issue, NOT the new routers/seed. The deploy (run `759f7824`) succeeded and the backend is healthy — every other endpoint (`/api/gallery`, `/api/auth/me`, `/api/content`, `/api/testimonials`, `/api/locations`, `/api/packages`) returns 200. `GET /api/students` 500s because **one legacy student document fails FastAPI response-model validation**, and FastAPI validates the *entire* list response — so a single bad row fails the whole endpoint and the Schüler-Liste shows nothing.

## Exact traceback (prod pod, run 759f7824)
```
ERROR:    Exception in ASGI application
Traceback (most recent call last):
  ...
  File ".../fastapi/routing.py", line 296, in app
    content = await serialize_response(
  File ".../fastapi/routing.py", line 155, in serialize_response
    raise ResponseValidationError(
fastapi.exceptions.ResponseValidationError: 1 validation errors:
  {'type': 'string_too_short',
   'loc': ('response', 0, 'last_name'),
   'msg': 'String should have at least 1 character',
   'input': '',
   'ctx': {'min_length': 1},
   'url': 'https://errors.pydantic.dev/2.13/v/string_too_short'}
INFO:     "GET /api/students HTTP/1.1" 500 Internal Server Error
```
`loc = ('response', 0, 'last_name')` → the item at index 0 of the returned list has `last_name = ""`, and the `Student` response model constrains `last_name` to `min_length=1`. pydantic v2.13 rejects it → `ResponseValidationError` → 500.

## The offending document (confirmed via read-only query on prod DB `driving-school-cms-test_database`, collection `students`)
Exactly **1** document matches `{ "last_name": "" }`:
```json
{
  "_id": "6a96c4c3a39c2ef37a55a01c",
  "first_name": "Künzler und Sauber AG",
  "last_name": "",
  "passed_date": "",
  "region": "",
  "created_at": "2026-09-01T12:27:47.386158+00:00"
}
```
This looks like a **company/organisation entry** (name in `first_name`, no surname). It also carries `passed_date = ""` and `region = ""` — empty strings that will likely fail validation too the moment `last_name` is fixed, if the `Student`/`Region` model types those as a date/enum or as `min_length`-constrained strings. pydantic reports only the first failure per field-set, so expect these next.

## Why preview passed but prod failed
Same code, different data. Preview's 8 students all have a valid `last_name`; prod has this one legacy/company row with empty `last_name` (+ empty `passed_date`/`region`). The new routers/models/seed are unrelated — startup completed and the backend serves all other routes.

## Answers to the four questions asked
1. **Traceback** — above. It is a `fastapi.exceptions.ResponseValidationError` (`string_too_short` on `response[0].last_name`), i.e. FastAPI *response* validation, not a query/DB error and not a crash in `routers/students.py` logic.
2. **Startup seed** — succeeded. Backend is up and serving; no seed/startup errors in the pod logs, and the new endpoints respond. The seed of `calendar_availability`, `pickup_locations`, etc. did not break `/api/students`.
3. **Packages** — not the cause. This is a deterministic response-validation rejection (pydantic 2.13), not an import error or a version-mismatch crash. No package diff is needed to explain the 500.
4. **Legacy document** — YES, confirmed: `_id 6a96c4c3a39c2ef37a55a01c` with `last_name=""` (also `passed_date=""`, `region=""`).

## Fix (E1 owns — pick one; ideally both)
**A. Data correction (fastest, unblocks prod now).** Fix the one row via the Deployment Panel → Database (DB Manager). Either set `last_name` to a real value (e.g. the company name / a placeholder like `"-"`), and give `passed_date`/`region` valid values — or delete the row if it isn't a real student. `_id = 6a96c4c3a39c2ef37a55a01c`.

**B. Make the endpoint resilient (prevents recurrence).** In the `Student` (and `Region`) response model, relax the constraints that reject legacy rows: allow empty `last_name` (drop `min_length=1` or make it `Optional`), and make `passed_date`/`region` tolerant of empty/missing values (`Optional`, or normalise `"" → None`). Alternatively, sanitise/skip invalid docs in the `GET /api/students` handler before returning so one bad row can't 500 the whole list. Then redeploy.

Recommended: do **A** immediately to restore the admin dashboard, and ship **B** so a future imperfect row can't take the list down again.
